# 给后续深化工作的项目说明

## 一句话定义

以 KuaiSearch-Lite 真实电商搜索行为为基础，做一个**电商搜索流量效率与需求机会诊断**项目：从搜索请求、商品曝光、点击和购买标签出发，找出值得运营跟进的搜索需求及品类，形成可验证的行动方案。

## 当前进度（2026-11-20）

**已经完成**：官方四份 Lite 文件下载与 SHA-256 校验；真实字段核查；Python + DuckDB SQL 本地管道；请求级和曝光级模型；质量审计；整体、品类、搜索需求、年龄段、相对时间指标；30 条候选机会的本地聚合表；[第一版业务报告](analysis-report.md)。已观察到 555,553 次搜索、17,800,904 次商品曝光，女装与部分高频搜索词存在值得复核的点击效率差距。

**尚未完成**：Power BI `.pbix` 文件、可公开的看板截图、搜索词与商品标题的逐项人工审阅、正式实验方案、GitHub 远程仓库与发布、简历最终条目。以上不能在简历中写成已完成成果。

## 面向岗位

主目标：电商搜索运营、流量运营、用户运营、数据运营实习。可展示的能力是数据理解、指标口径、SQL 建模、异常审计、分群分析、机会排序、业务解释、看板呈现、实验方案设计。不能用这批数据证明完整交易运营、GMV 增长、长期留存或线上实验效果。

## 交付物与其区别

1. **GitHub 仓库**：项目主页，放源代码、SQL、数据字典、复现步骤、指标口径、可公开的图表和报告。它是简历链接的入口。
2. **分析报告**：说明业务问题、数据来源、观察证据、优先级、运营动作、实验设计与局限。面试时重点讲这份报告。
3. **交互看板**：Power BI 读取聚合结果，展示整体漏斗、品类结构、搜索需求机会和相对时间趋势。它是分析的查看界面，不代替报告。
4. **本地分析数据库**：DuckDB 保留请求级和曝光级事实表，用来复算；用户级原始数据不发布。

项目不是要搭建一个真实搜索引擎，也不是面向商家的在线运营平台。只有在未来需要给他人持续提供数据服务时，才考虑开发平台。

## 第一版实施路线

1. 从官方固定版本下载四份 Lite 数据，验证大小与 SHA-256，保存来源清单。
2. 检查主键、字段、列表重复、点击和购买是否在曝光内、商品与用户关联覆盖。
3. 以 SQL 建立搜索请求层、商品曝光层和本地搜索词字典。
4. 计算整体、品类、搜索需求、年龄段和相对时间区间的曝光、点击、购买标签指标。
5. 设置样本量门槛，生成高曝光低点击候选，并利用官方 train/test 划分做方向复核。
6. 人工审阅候选的搜索词与商品供给，写出 2–3 条“证据 → 假设 → 运营动作 → 实验指标”。
7. 制作 Power BI 看板，撰写中文业务报告、GitHub README 和简历项目条目。

## 技术适配优先级

| 技术 | 适合程度 | 何时加入 |
| --- | --- | --- |
| Python | 必需 | 下载、校验、数据管道、报告生成 |
| SQL + DuckDB | 必需 | 单机处理约千万条曝光与聚合分析 |
| Power BI | 高 | 可视化和面试演示；只加载聚合数据 |
| ClickHouse | 中 | 若做交互式多维查询、性能对比，可作为扩展 |
| Spark | 中 | 若要求大数据工程能力，可迁移全量数据管道并比较耗时与成本 |
| Hive / Hadoop | 低 | 当前 Lite 单机数据规模下缺乏必要性；企业集群场景再使用 |
| Flink | 低 | 数据是离线快照，没有实时流；只有引入模拟实时事件且清楚标注时使用 |
| LangChain | 低 | 可做报告检索或洞察草稿辅助，但不是指标计算依据；需人工复核 |

建议先把 Python、SQL、Power BI 与运营动作做扎实，再选择 **ClickHouse 或 Spark 中的一个**作为有可测价值的增强。简历只写实际运行过、能解释架构与取舍的工具。

## 重要限制

- `time_index` 为相对编码，不能转换成真实日期、小时、星期，也不能写“近 30 天”趋势。
- Lite 为样本，不把样本点击率、购买率当作平台真实水平。
- 同一次搜索的购买标签不等于支付完成订单；没有金额字段，不能算 GMV。
- 训练段与测试段用于方向性复核，不是随机 A/B 实验。
- 运营动作在项目中只是方案；没有线上实施和对照组时，不报告提升百分比。
