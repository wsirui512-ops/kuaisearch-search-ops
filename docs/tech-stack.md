# 技术栈与选型说明

原则：只写实际运行过、能解释取舍的技术；没有落地的方案不写进简历。

## 1. 实际使用的技术栈

| 组件 | 版本 | 角色 | 状态 |
| --- | --- | --- | --- |
| Python | 3.13 | 下载校验、管道编排、统计与导出 | ✅ 已运行 |
| DuckDB | 2.0.0 | 单机列存分析库，1,780 万行曝光聚合 | ✅ 已运行 |
| SQL（DuckDB 方言） | — | staging / intermediate / marts 三层建模 | ✅ 已运行 |

## 2. 为什么主引擎是 DuckDB

- 数据 3.08 GB、1,780 万条曝光行，单机足够；DuckDB 直接读 JSONL、列存、无需部署。
- 全量重建（读 3 GB JSONL + 建曝光表 + 全部聚合 + 导出）实测约 40 秒，迭代成本低。
- 复现门槛低：一条 `pip install duckdb` 就能跑，不依赖集群和服务。

**取舍**：DuckDB 不适合多用户并发点查。如果未来要把结果做成在线服务，需要引入服务型 OLAP 引擎——那属于另一个阶段的工程问题，当前数据规模不需要。

## 3. Spark 的位置：对账，不是主线

| 项 | 值 |
| --- | --- |
| 环境 | Java 21 + Spark 4.3.0（bin-hadoop3） |
| 启动 | 5.8 秒 |
| sessions 聚合（556k 行） | 1.4 秒 |
| 类目 × 条数（1,780 万曝光） | 2.2 秒 |
| 与 DuckDB 对账 | 5 个核心指标完全一致（`outputs_public/spark_check.json`） |

**为什么不做主线**：3 GB 数据用 Spark 是过度设计，DuckDB 40 秒就能重建全部结果。Spark 在这里的价值是**证明指标不依赖单一引擎**，以及为将来处理官方全量（约 107 GB）留出分区与迁移路径。

面试被问"为什么不直接用 Spark"时的答法：主线要的是可复现和口径一致，不是堆引擎；Spark 负责对账与全量迁移验证。

## 4. 看板为什么是静态渲染

八页报告由 `scripts/build_static_dashboard.py` 从 `outputs_public/` 生成 PPTX，再由 `scripts/export_dashboard.py` 渲染成 PNG 与 PDF。这样做的好处：

- 数字直接来自聚合结果，和报告、CSV 完全同步；
- 改一个指标只需要重跑两条命令，不依赖任何商业软件；
- 仓库里能直接看到 PDF 和截图，面试官不必安装软件。

代价：没有交互筛选。网页版 `dashboards/preview.html` 提供可点击的补充视图。

## 5. 工程约束

| 约束 | 做法 |
| --- | --- |
| 导出可复现 | 浮点保留 10 位有效数字 + 稳定排序键；两次重建 14 个 CSV 哈希一致 |
| 管道安全 | 先建临时库，全部断言通过后才替换正式库；失败不删旧库 |
| 数据质量 | 39 项断言（请求=会话、曝光=求和、位置越界 0、意图覆盖 100%） |
| 跨引擎一致 | DuckDB(库) / DuckDB(Parquet) / 纯 Python / Spark 四路对账 |
| 发布边界 | 原始数据、DuckDB、Parquet、query 明细不发布；聚合结果可发布 |
