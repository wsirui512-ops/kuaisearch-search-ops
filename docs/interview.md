# 面试材料：讲法、追问、简历表述

> 全部数字来自本仓库的可复算结果（`python run.py`）。不要背数字，背**逻辑链**。

## 1. 30 秒版本

> "我用快手电商搜索的公开数据，分析『哪些搜索需求有曝光但没被接住』。一开始我也按常规看各品类点击率，发现女装最低；但深挖后发现，真正决定单件点击率的是结果列表长度——7% 的请求展示 100 条以上，贡献了 40% 的曝光。按同条数校准后，品类差异基本消失，只剩 124 个泛品类词有真实缺口，我给出了三个可做实验的运营动作。"

## 2. 2 分钟版本（结构）

1. **业务问题**：搜索运营要判断"该治理哪些词"，常见做法是看高曝光低点击。
2. **数据**：55.5 万请求、1780 万曝光、10 万用户；没有订单金额，购买只是标签。
3. **口径陷阱**：商品点击率 vs 请求点击率；列表长度从 1–10 到 100+，单件点击率 8.96% → 2.19%。
4. **校准**：同条数期望点击 → 残差；女装差距 0.78pp → 0.25pp；需求标签差异 ≈ 0。
5. **真机会**：124 个词仍有缺口，Top 30 缺口约 6,400 次点击（1% 曝光）；鞋子/衣服/外套/裤子/手机壳。
6. **动作**：首屏收敛、细意图入口、商品信息补全；每个都有主指标、护栏、最小样本。
7. **限制**：观察性、非因果、无 GMV、无线上实验。

## 3. 高频追问与答法

**Q1：为什么不用 GMV / 转化率？**
没有价格、订单、支付字段。购买是"同一次搜索内被购买的商品标签"，且 1,438 个购买商品不在同次点击列表，不能当严格漏斗。硬算 GMV 会造假。

**Q2：为什么说"列表长"不是"搜索词差"？**
三条证据：① 同一批数据里，条数从 1–10 到 100+，点击率单调下降 8.96%→2.19%；② 控制条数后，品类/标签差距大幅收窄；③ 长列表请求点击率 84%，说明用户仍能点到东西，不是"搜不到"。

**Q3：这批数据能得出因果吗？**
不能。所有结论都是同条数条件下的相关性；动作是假设，需要 A/B 验证。我在文档里写死了这一点。

**Q4：p 值 1e-50 说明效果很大吗？**
不说明。样本量大，微小差异也会显著。我看 gap_pp、置信区间和缺口点击；FDR 校正后 124 个里只有 74 个显著。

**Q5：训练/测试怎么分的？**
按时间切的：train 1–936,724，test 936,726–965,265。所以只能做"时间外方向复核"，不能当 A/B。

**Q6：为什么不用 Spark / ClickHouse？**
3GB 数据用 DuckDB 单机 40 秒重建，Spark 是负分。ClickHouse 留给"结果要做并发看板服务"的场景，我写了对账方案，但没装 Docker，所以不写进简历。

**Q7：为什么 query 用 md5 做 key？**
DuckDB 的字符串排序和其他引擎不完全一致，row_number 会漂移；md5 保证同一 query 在任何引擎都是同一个 key。

**Q8：需求标签怎么来的？准确率多少？**
规则 + 人工抽检（`outputs/intent_review_sample.csv` 200 条）。它是可审计的启发式，不是模型；标签层面的差异已经很小，结论不依赖标签精度。

**Q9：如果让你继续做，下一步是什么？**
① 100 条商品级人工审阅（query × 标题属性覆盖）；② 补 Power BI 看板；③ 装 Docker 后做 ClickHouse 对账；④ 用真实流量把"曝光数"换算成实验天数。

**Q10：这个项目最难的地方？**
不是写 SQL，是发现"我差点用一个被条数污染的指标下结论"，然后把口径重做了一遍。

## 4. 简历表述（可直接用，数字已核对）

- 基于 55.5 万次真实电商搜索与 1780 万次商品曝光，用 Python + DuckDB 搭建 staging/intermediate/marts 三层 SQL 管道，40 秒可全量重建并自动对账。
- 发现"结果条数"主导商品点击率（1–10 条 8.96% → 100+ 条 2.19%），建立同条数基准与残差口径，将品类效率差距从 0.78pp 校准到 0.25pp；筛出 124 个真实缺口搜索词（74 个 FDR 校正后显著，Top 30 缺口约 6,400 次点击）。
- 将诊断转化为 3 个可执行搜索运营动作（首屏收敛、细意图入口、商品信息补全），配套主指标/护栏指标与最小样本量估算，形成完整 A/B 实验方案。
